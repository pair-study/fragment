# PRD: 일감 — 스케줄부터 급여까지 관리하는 근무 플랫폼

> **일하는 모든 순간을 정확하고 투명하게**
>
> 소·중형 단일 매장부터 다점포 사업장까지, 근무 스케줄 편성과 급여 계산을 자동화하는 SaaS

---

## 1. 배경

### 현재 문제

- 업종마다 룰이 다른 스케줄(고정 요일제, 주단위 로테이션, 단기 집중형)을 수기로 맞추는 과정의 비효율.
- 다양한 근무 형태에 따른 주휴·야간·공휴일(특일) 등 복잡한 수당 계산에서 발생하는 휴먼 에러.
- 불투명한 급여 산정 기준으로 인한 관리자–근로자 간 정보 비대칭과 불신.

### 서비스 당위성

- **최저임금 인상·주 52시간 정착**: 수당 계산의 법적 정확성 부담이 높아졌고, 계산 실수 한 번이 노동 분쟁으로 이어질 수 있다.
- **다양한 운영 규모**: 단일 매장 소상공인부터 다점포 운영자까지, 매장 수와 무관하게 교대근무 관리의 복잡도가 공통적으로 높다.
- **기존 도구의 한계**:
  - 수기/엑셀: 매장 수가 늘거나 인원이 많아지면 주휴수당 합산·대타 조율이 한계에 부딪힌다.
  - 범용 스케줄러(구글 캘린더 등): 노동법 기반 수당 계산이 없고 다점포 집계가 불가능하다.
  - 대형 ERP(SAP, Oracle): 소·중형 사업자가 감당하기엔 비용·도입 기간이 과도하다.

### 관련 문서 / 레퍼런스

- Shiftee — https://shiftee.io/ko/scheduler
- 하우머치 (Howmuch) — 조직 생성/초대, 세금·4대보험 설정 흐름 참고
- Deputy, 7shifts — 글로벌 다점포 교대근무 SaaS 구조 참고

## 2. 목표

### 사용자가 무엇을 할 수 있어야 하는가

- **관리자**: AI 추천으로 주간 스케줄 초안을 자동 생성하고, 근태·급여를 한 곳에서 관리한다.
- **근로자**: 희망 근무를 앱에서 신청하고, 확정 스케줄·대타·급여 명세를 투명하게 확인한다.
- **공통**: 수당이 자동 계산되어, 산정 기준이 양측에 동일하게 보인다.

### 정량 목표

- 주간 스케줄 편성 시간 **70% 이상 단축** (AI 자동 추천 대비 수기 편성 기준)
- 급여 계산 오류 **0 지향** (주휴·야간·연장 수당 자동화)
- 관리자–근로자 간 **급여 정산 분쟁 감소**

## 4. 범위

> 페이즈 분류 기준: "이 기능 없이 핵심 루프(희망 신청 → 스케줄 확정 → 급여 정산)가 돌아가는가"

### Phase 1 — MVP: 핵심 서비스 루프 + 전체 플랫폼

**관리자 (`apps/web`, 데스크탑 전용 — 반응형 미지원)**

- [ ] 계정 및 조직 관리 (이메일+비밀번호 가입, 조직 CRUD, 다중 조직 스위칭)
- [ ] 인력 관리 (근로자 초대 링크, 스케줄 타입·임금명세서 템플릿 지정, 퇴사 처리)
- [ ] 스케줄 자동 추천 (규칙 기반 constraint satisfaction) + 수동 조정 + 확정
- [ ] 근태 확인·확정 (GPS 출퇴근 체크, 지각·연장 하이라이팅, 수정 요청 승인, 관리자 직접 입력)
- [ ] 급여 계산 (시급×근무시간 + 주휴·야간·연장·공휴일 수당) + 명세서 발급

**근로자 (`apps/mobile`, Expo 네이티브 앱 — iOS·Android)**

- [ ] 카카오 / 네이버 소셜 로그인
- [ ] 다중 조직 소속 및 전환
- [ ] 희망 근무 신청 (불가/제약 입력 방식)
- [ ] 확정 스케줄 확인
- [ ] GPS 기반 출퇴근 체크 (버튼 방식)
- [ ] 근태 수정 요청
- [ ] 급여 명세 확인 + 근태 서명/동의
- [ ] 1:1 스케줄 교환 요청 및 수락/거절
- [ ] Push 알림 (Expo Notifications) — 스케줄 확정·변경, 교환 요청, 퇴근 미처리 등

**인프라**

- [ ] AWS EC2 (NestJS API 서버)
- [ ] AWS S3 + CloudFront (Next.js 정적 호스팅)
- [ ] GitHub Actions CI/CD (테스트 자동화 + 자동 배포)

### Phase 2 — 고도화

- [ ] 관리자 웹 반응형 지원 (태블릿·모바일에서 관리자 접근 가능)
- [ ] 다점포 통합 뷰 (없으면 매장별로 따로 확인 가능)
- [ ] 조직 이전 기능 (관리자 탈퇴 시 다른 관리자 계정으로 조직 이전)
- [ ] 스케줄 알고리즘 고도화 (fairness — 근로자 간 균등 배분)
- [ ] 다중 기기 Expo 푸시 토큰 지원 (MVP는 기기 1대 기준, 재설치 시 덮어씀)

### 이번 작업에 포함하지 않음

- [ ] 4대보험/세무 신고 연동 (외부 기관 전송)
- [ ] 급여 실지급 (이체/송금) 연동
- [ ] WiFi 기반 체크인 (GPS 불가 대체 수단)
- [ ] 다점포 간 스케줄 교환
- [ ] 다국어/해외 노동법 대응

## 5. 사용자 흐름

### 5.1 사용 시나리오

**시나리오 1 — 주간 스케줄 편성 (최성민, 페르소나 A)**

> 최성민은 매주 월요일 다음 주 스케줄을 짠다. 일감에서 FLEXIBLE 직원들의 희망 신청 마감을 확인하고, AI 추천 버튼을 누른다. 시스템이 직원 제약 조건과 시간대별 최소 인원 조건을 반영한 초안을 생성하고, 인원이 부족한 시간대를 빨간색으로 하이라이팅한다. 최성민은 해당 시간대를 수동으로 조정하고 확정한다. 직원들에게 Push 알림이 자동 발송된다.

**시나리오 2 — 급여 정산 (최성민 → 김하은, 페르소나 A·C)**

> 월말, 최성민은 직원들의 근태를 확인하고 급여 계산을 실행한다. 주휴수당·야간수당이 자동 계산된 명세서가 생성되고, 김하은의 앱에 발급 알림이 전송된다. 김하은은 앱에서 항목별 계산 근거를 확인하고 서명한다.

**시나리오 3 — 스케줄 교환 (김하은, 페르소나 C)**

> 김하은은 다음 주 토요일 개인 사정이 생겨 같은 매장 동료에게 1:1 교환을 요청한다. 동료가 24시간 내 수락하면 최성민에게 최종 승인 요청이 전송되고, 승인 후 양측 스케줄이 자동으로 반영된다.

## 6. 기능 요구사항

> **조직 관리 vs 인력 관리 분리 원칙**
>
> - **조직 관리** (FR-1): 매장 자체의 설정값 풀(pool)을 정의한다 — 임금명세서 템플릿 목록, 시간대별 최소 인원 조건, GPS 반경, 정기 휴무일, 법정 공휴일 정책, 스케줄 신청 기간, 1:1 교환 허용 여부.
> - **인력 관리** (FR-5): 근로자 개인에게 그 풀에서 값을 지정한다 — 어떤 템플릿을 쓸지, 스케줄 타입(FIXED/FLEXIBLE), FIXED의 경우 고정 스케줄.
>
> 관리자는 조직 설정에서 "사용 가능한 옵션"을 먼저 만들고, 인력 관리에서 근로자별로 "어떤 옵션을 쓸지" 지정한다.

### FR-1. 계정 및 조직 관리

#### FR-1.1 관리자 계정

> 관리자는 이메일·비밀번호로 계정을 생성하고 관리할 수 있어야 한다. 서비스에 접근하고 조직 운영을 시작하기 위해서다.

**Acceptance Criteria**

- [ ] 이름·이메일·비밀번호로 가입할 수 있다.
- [ ] 비밀번호를 잊었을 때 이메일로 재설정 링크를 받아 30분 이내 변경할 수 있다.
- [ ] 탈퇴 시 계정과 조직이 소프트 딜리트되며 근태·급여 이력은 3년 보존된다.

#### FR-1.2 근로자 계정

> 근로자는 카카오 또는 네이버 소셜 로그인으로 가입·로그인할 수 있어야 한다. 별도 계정 없이 익숙한 플랫폼으로 빠르게 서비스에 접근하기 위해서다.

**Acceptance Criteria**

- [ ] 카카오/네이버 OAuth로 최초 가입과 재로그인이 가능하다.
- [ ] 같은 이메일로 다른 소셜 플랫폼 가입 시도 시 기가입 플랫폼을 안내한다.
- [ ] 미정산 급여가 있으면 정산 완료 전까지 탈퇴가 불가하다.

#### FR-1.3 조직 생성

> 관리자는 매장 정보와 운영 조건을 입력해 조직을 생성할 수 있어야 한다. 스케줄·근태·급여 관리의 기반 설정을 완료하기 위해서다.

**Acceptance Criteria**

- [ ] 사업자번호(국세청 API 검증)·업장명·위치(도로명주소)를 필수 입력할 수 있다.
- [ ] 시간대별 최소 인원 조건, 정기 휴무일, 법정 공휴일 정책을 설정할 수 있다.
- [ ] FLEXIBLE 근로자 대상 스케줄 신청 기간(단위·마감·조정 기간·자동 반복)을 설정할 수 있다.
- [ ] GPS 허용 반경(50m~300m, 기본 100m)과 1:1 교환 허용 여부를 설정할 수 있다.

#### FR-1.4 조직 수정

> 관리자는 조직 설정을 언제든 수정할 수 있어야 한다. 운영 환경 변화에 맞게 유연하게 조정하기 위해서다.

**Acceptance Criteria**

- [ ] 조직 생성 시 입력한 모든 항목을 수정할 수 있다.

#### FR-1.5 조직 삭제

> 관리자는 더 이상 운영하지 않는 조직을 삭제할 수 있어야 한다. 불필요한 조직 없이 관리 부담을 줄이기 위해서다.

**Acceptance Criteria**

- [ ] 소속 근로자 전원 퇴사 처리 후에만 삭제할 수 있다.
- [ ] 삭제 후 근태·급여 데이터는 3년 보존된다.

#### FR-1.6 다중 조직 관리

> 다점포 관리자는 한 계정으로 여러 조직을 전환하며 관리할 수 있어야 한다. 매장마다 별도 계정 없이 효율적으로 다점포를 운영하기 위해서다.

**Acceptance Criteria**

- [ ] 한 계정으로 여러 조직을 생성하고 운영할 수 있다.
- [ ] 조직 전환 즉시 해당 조직의 데이터로 컨텍스트가 전환된다.

---

### FR-2. 스케줄 관리

> 스케줄 상태 전이 상세는 `docs/SPEC.md` FR-2 참조.

#### FR-2.1 희망 근무 신청

> FLEXIBLE 근로자는 안되는 날짜와 시간대만 앱에서 입력할 수 있어야 한다. 개인 사정이 반영된 스케줄을 받기 위해서다.

**Acceptance Criteria**

- [ ] 신청 기간이 오픈되면 날짜별로 불가 / 시간 제약을 입력할 수 있다.
- [ ] 미입력 날짜는 전일 근무 가능으로 자동 처리된다.
- [ ] 마감 전까지 수정 가능하며, 마감 후에는 입력이 비활성화된다.

#### FR-2.2 FIXED 스케줄 자동 반영

> 관리자는 고정 근로자의 요일별 근무 패턴을 한 번 설정하면 스케줄이 자동으로 생성되어야 한다. 매월 반복 입력 없이 고정 근무자를 관리하기 위해서다.

**Acceptance Criteria**

- [ ] 요일별 시작·종료 시간을 설정하면 지정 기간에 `PUBLISHED` 스케줄이 자동 생성된다.
- [ ] 정기 휴무일·법정 공휴일 정책에 따라 해당일은 자동 제외된다.
- [ ] 변경 반영 시점을 즉시 다음 근무 / 다음 주 / 다음 달 / 직접 입력 중 선택할 수 있다.

#### FR-2.3 스케줄 자동 추천

> 관리자는 근로자들의 희망 신청을 바탕으로 최적 스케줄 초안이 자동 생성되어야 한다. 수기 편성 시간을 줄이고 노동법 제약을 자동으로 반영하기 위해서다.

**Acceptance Criteria**

- [ ] "AI 추천 실행" 버튼으로 FLEXIBLE 근로자의 신청 기반 `DRAFT` 초안이 생성된다.
- [ ] 시간대별 최소 인원 충족(✅) / 경고(⚠️) / 미충족(❌)을 Explainable UI로 확인할 수 있다.
- [ ] 20명·5매장 기준 3초 이하로 응답한다.

#### FR-2.4 스케줄 확정 및 알림

> 관리자는 초안을 검토·수정한 뒤 확정할 수 있어야 한다. 근로자들이 즉시 확정 스케줄을 알림으로 받고 출근을 준비할 수 있게 하기 위해서다.

**Acceptance Criteria**

- [ ] 확정 시 `DRAFT` → `PUBLISHED`로 상태가 변경된다.
- [ ] 해당 근로자에게 Expo Push 알림이 발송된다.
- [ ] 확정과 동시에 해당 근로자의 근태 레코드(`EXPECTED`)가 자동 생성된다.

#### FR-2.5 1:1 스케줄 교환

> 근로자는 같은 조직의 동료와 스케줄 교환을 요청할 수 있어야 한다. 개인 사정이 생겼을 때 스스로 대타를 구하기 위해서다.

**Acceptance Criteria**

- [ ] 신청자 요청 → 상대방 24시간 내 수락/거절 → 관리자 최종 승인의 3단계 흐름으로 처리된다.
- [ ] 미응답 시 24시간 후 자동 취소된다.
- [ ] 교환 성사 시 기존 스케줄은 `CANCELLED`, 새 스케줄은 `PUBLISHED`로 생성된다.
- [ ] 교환은 동일 조직 내에서만 허용된다.

### FR-3. 근태 관리

> 근태 레코드 상태 전이 상세는 `docs/SPEC.md` FR-3 참조.

#### FR-3.1 GPS 기반 출퇴근 체크

> 근로자는 앱에서 버튼 한 번으로 출퇴근을 기록할 수 있어야 한다. 별도 기기 없이 정확한 근태를 남기기 위해서다.

**Acceptance Criteria**

- [ ] 출근 체크는 조직의 GPS 허용 반경 내에서만 가능하다.
- [ ] 퇴근 체크 시 연장 근무 여부를 선택하고 실제 종료 시각을 입력할 수 있다.
- [ ] 다중 조직 근로자는 조직 전환 후 해당 매장 반경 기준으로 체크인한다.

#### FR-3.2 지각·연장 하이라이팅

> 관리자는 지각·연장이 발생한 근로자를 근태 화면에서 한눈에 파악할 수 있어야 한다. 수당 처리 여부를 빠르게 판단하기 위해서다.

**Acceptance Criteria**

- [ ] 예정 출근 시각보다 늦은 체크인은 지각으로 하이라이팅된다.
- [ ] 근로자가 연장 근무를 선택한 경우 연장 여부와 실제 종료 시각이 하이라이팅된다.

#### FR-3.3 퇴근 미처리 자동화

> 근로자가 퇴근 체크를 하지 않았을 때 시스템이 자동으로 알림을 보내고 미처리 상태로 전환해야 한다. 미처리 근태를 놓치지 않고 정확한 급여 계산을 하기 위해서다.

**Acceptance Criteria**

- [ ] 예정 퇴근 시각 +30분, +2시간에 근로자에게 Push 알림이 발송된다.
- [ ] 예정 퇴근 시각 +12시간까지 미처리 시 `UNPROCESSED`로 자동 전환되고 관리자 대시보드 미처리 목록에 표시된다.

#### FR-3.4 근태 수정 요청

> 근로자는 GPS 오류 등으로 잘못 기록된 근태를 수정 요청할 수 있어야 한다. 실제 근무 내역이 정확하게 반영되어 급여가 올바르게 계산되도록 하기 위해서다.

**Acceptance Criteria**

- [ ] 출근/퇴근/연장 시각과 사유를 입력해 수정 요청을 제출할 수 있다.
- [ ] 관리자 승인 시 근태 레코드가 업데이트되고 감사 로그가 보존된다.
- [ ] 관리자 거절 시 기존 기록이 유지되고 근로자에게 알림이 발송된다.

#### FR-3.5 관리자 직접 입력

> 관리자는 앱 오류 등 예외 상황 시 근로자의 출퇴근 시각을 직접 입력할 수 있어야 한다. 시스템 오류로 인한 근태 공백 없이 정확한 기록을 유지하기 위해서다.

**Acceptance Criteria**

- [ ] 관리자가 직접 입력한 내역은 감사 로그에 별도 기록된다.
- [ ] 직접 입력 후 해당 근로자에게 변경 Push 알림이 발송된다.

#### FR-3.6 근태 확정 및 서명

> 근로자는 정산 전 자신의 근태 내역을 확인하고 동의할 수 있어야 한다. 급여 산정 기준을 투명하게 확인하고 신뢰성 있는 정산이 이루어지도록 하기 위해서다.

**Acceptance Criteria**

- [ ] 정산 기간의 근태 목록을 조회하고 동의 버튼으로 서명할 수 있다.
- [ ] 서명 즉시 급여 계산이 자동으로 트리거된다.
- [ ] 서명 후 수정 요청 시 서명 상태가 초기화되고 재서명이 필요하다.

### FR-4. 급여 계산 엔진

> **임금명세서 템플릿 항목** — 조직 관리에서 생성 후 근로자별 지정. 세금·보험, 월급일, 급여 기준, 휴무 처리, 결근 처리, 주휴수당, 야간수당, 연장수당, 공휴일 수당, 기타(상여·비과세)로 구성된다. 항목별 선택 값 상세는 `docs/SPEC.md` FR-4 참조.

#### FR-4.1 급여 자동 계산

> 근로자 서명 완료 후, 확정 근태와 임금명세서 템플릿을 기반으로 급여가 자동 계산되어야 한다. 관리자의 수작업 없이 정확한 급여가 산정되도록 하기 위해서다.

**Acceptance Criteria**

- [ ] 기본급·주휴수당·야간·연장·공휴일 수당·공제 항목이 템플릿 설정에 따라 자동 계산된다.
- [ ] 1초 이하로 응답한다.
- [ ] `UNPROCESSED` 근태는 제외하고 계산되며 명세서에 표시된다.

#### FR-4.2 급여 계산 트리거

> 근로자가 서명하는 즉시 급여 계산이 자동으로 시작되어야 한다. 관리자가 별도로 조작하지 않아도 정산이 자동으로 진행되도록 하기 위해서다.

**Acceptance Criteria**

- [ ] 근로자 서명 시 해당 근로자의 급여 계산이 자동 실행된다.
- [ ] 여러 근로자가 동시에 서명한 경우 병렬로 처리된다.
- [ ] 계산 완료 시 관리자 화면에 완료 상태가 표시된다.

#### FR-4.3 급여 명세서 발급

> 관리자는 급여 계산 결과를 명세서로 발급할 수 있어야 한다. 근로자가 항목별 산정 기준을 투명하게 확인할 수 있게 하기 위해서다.

**Acceptance Criteria**

- [ ] 계산 완료된 근로자에 대해 발급 버튼이 활성화된다.
- [ ] 발급 즉시 근로자에게 Push 알림이 발송된다.
- [ ] 근로자는 앱에서 기본급·수당·공제·실수령액을 항목별로 조회할 수 있다.

#### FR-4.4 급여 계산 감사 로그

> 관리자는 급여 계산 이력을 추적할 수 있어야 한다. 분쟁 발생 시 계산 기준과 변경 내역을 근거로 제시하기 위해서다.

**Acceptance Criteria**

- [ ] 급여 계산 실행마다 계산 시각·기준 스냅샷·결과가 기록된다.
- [ ] 재계산 시 별도 이력이 남는다.
- [ ] 관리자가 조회 가능하며 3년 보존된다.

### FR-5. 인력 관리

#### FR-5.1 근로자 초대·등록

> 관리자는 초대 링크로 근로자를 조직에 등록하고 스케줄 타입·급여 조건을 설정할 수 있어야 한다. 근로자가 빠르게 합류해 스케줄·급여 관리를 즉시 시작할 수 있게 하기 위해서다.

**Acceptance Criteria**

- [ ] 초대 링크는 7일간 유효하며 다수가 동시에 사용 가능하다. 관리자가 언제든 무효화·재발급할 수 있다.
- [ ] 링크 접속 후 소셜 로그인 시 조직에 자동 연결된다.
- [ ] 스케줄 타입(FIXED/FLEXIBLE)과 임금명세서 템플릿을 지정해야 저장된다.
- [ ] FIXED 선택 시 요일별 근무 시간과 변경 반영 시점(즉시 다음 근무 / 다음 주 / 다음 달 / 직접 입력)을 추가 설정한다.

#### FR-5.2 퇴사 처리

> 관리자는 계약이 종료된 근로자를 퇴사 처리할 수 있어야 한다. 스케줄 편성 대상에서 제외하고 접근 권한을 정리하기 위해서다.

**Acceptance Criteria**

- [ ] 퇴사 처리 시 해당 조직에 대한 기능 접근이 불가해진다 (다른 조직 소속은 유지).
- [ ] 확정된 미래 스케줄은 `CANCELLED` 처리된다.
- [ ] 근태·급여 데이터는 3년 보존된다.

#### FR-5.3 퇴직자 데이터 조회

> 관리자는 퇴사한 근로자의 근태·급여 이력을 조회할 수 있어야 한다. 법적 보존 기간 동안 필요 시 기록을 확인하기 위해서다.

**Acceptance Criteria**

- [ ] 기간 필터로 퇴직자의 근태·급여 이력을 조회할 수 있다.

#### FR-5.4 근로자 다중 조직

> 근로자는 여러 조직에 동시 소속되어 각 조직의 스케줄·근태·급여를 앱에서 별도로 관리할 수 있어야 한다. 투잡 등 여러 매장에서 일해도 하나의 앱으로 모든 근무를 관리하기 위해서다.

**Acceptance Criteria**

- [ ] 앱 내 조직 전환으로 각 조직의 데이터를 독립적으로 조회할 수 있다.
- [ ] 시급·스케줄 타입·임금명세서 템플릿은 조직별로 별도 지정된다.
- [ ] 출근 체크는 현재 선택된 조직의 GPS 반경 기준으로 동작한다.

### FR-6. 대시보드

#### FR-6.1 관리자 대시보드

> 관리자는 스케줄·근태·급여·인력 관리를 웹 대시보드 한 곳에서 처리할 수 있어야 한다. 여러 시스템을 오가지 않고 업무를 효율적으로 처리하기 위해서다.

**Acceptance Criteria**

- [ ] 스케줄 희망 신청 취합, AI 추천 실행, 확정, 1:1 교환 승인/거부를 할 수 있다.
- [ ] 근태 확인·지각연장 하이라이팅·수정 승인·직접 입력, 급여 계산·명세서 발급을 할 수 있다.
- [ ] 임금명세서 템플릿 CRUD, 조직 설정 관리를 할 수 있다.
- [ ] 데스크탑 전용 (반응형 미지원, `apps/web`).

#### FR-6.2 근로자 앱

> 근로자는 모바일 앱 하나로 근무 관련 모든 작업을 처리할 수 있어야 한다. 별도 시스템 없이 스마트폰으로 편리하게 근무를 관리하기 위해서다.

**Acceptance Criteria**

- [ ] 조직 전환, 희망 근무 신청, 확정 스케줄 확인, GPS 출퇴근 체크, 근태 수정 요청, 급여 명세 확인 및 서명, 1:1 교환 요청, Push 알림 수신이 가능하다.
- [ ] iOS·Android 네이티브 앱(Expo)으로 제공된다 (`apps/mobile`).

## 7. 비기능 요구사항

- **성능**:
  - 스케줄 화면 LCP(최대 콘텐츠 풀인트) **2.5초 이하**
  - AI 스케줄 추천 응답 **3초 이하** (20명·5매장 기준)
  - 급여 계산 응답 **1초 이하**
- **플랫폼**:
  - 관리자: 데스크탑 웹 (`apps/web`, 반응형 미지원)
  - 근로자: Expo 네이티브 앱 (`apps/mobile`, iOS·Android)
- **접근성**: 모바일 최소 폰트 14px, 명도 대비 WCAG AA 기준.
- **보안**: 급여·개인정보 암호화, 조직 간 데이터 격리(Row-level security), 사업자번호 검증.
- **정확성/규정**: 노동법 기반 수당 계산 정확성 — 최저임금·주휴수당·공휴일 규정 변경 시 엔진 업데이트 대응.
- **로깅/모니터링**: 급여 계산 감사 로그, 스케줄 변경 이력 추적, 관리자 직접 입력 이력 추적.

## 8. 리스크

> 기술 구현 리스크는 `docs/TEST_PLAN.md`에서 관리한다.

- **Cold start 문제**: 양면 플랫폼 특성상 관리자가 없으면 근로자 유입도 없다. 초기 관리자 확보 전략 없이는 플랫폼이 작동하지 않으며, 관리자 온보딩에 집중하는 초기 런칭 전략이 필요하다.
- **전환 저항**: 엑셀·수기 방식에 익숙한 소상공인이 새 도구 도입을 꺼릴 수 있다. 온보딩 과정에서 마찰이 크면 이탈로 이어지므로 초기 설정 흐름을 최대한 단순하게 설계해야 한다.
- **경쟁 서비스 대응**: Shiftee 등 기존 서비스 대비 수당 자동 계산과 근로자-관리자 간 투명성이라는 차별점이 실제로 체감되지 않으면 전환 동기가 약하다.
- **노동법 변경 리스크**: 최저임금 인상, 주휴수당 기준 변경 등 법 개정 시 급여 엔진 업데이트가 지연되면 계산 오류가 발생해 신뢰도에 직접 타격이 간다. 법 개정 모니터링과 신속 대응 체계가 필요하다.
