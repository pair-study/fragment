# PRD: 일감 — 스케줄부터 급여까지 관리하는 근무 플랫폼

> **일하는 모든 순간을 정확하고 투명하게**
>
> 소·중형 단일 매장부터 다점포 사업장까지, 근무 스케줄 편성과 급여 계산을 자동화하는 SaaS

---

## 1. 배경

### 현재 문제

- 업종마다 룰이 다른 스케줄(고정 요일제, 주단위 로테이션, 단기 집중형)을 수기로 맞추는 과정의 비효율.
- 다양한 근무 형태에 따른 주휴·야간·공휴일(특일) 등 복잡한 수당 계산에서 발생하는 휴먼 에러.
- 불투명한 급여 산정 기준으로 인한 관리자–근무자 간 정보 비대칭과 불신.

### 서비스 당위성

- **최저임금 인상·주 52시간 정착**: 수당 계산의 법적 정확성 부담이 높아졌고, 계산 실수 한 번이 노동 분쟁으로 이어질 수 있다.
- **다양한 운영 규모**: 단일 매장 소상공인부터 다점포 운영자까지, 매장 수와 무관하게 교대근무 관리의 복잡도가 공통적으로 높다.
- **기존 도구의 한계**:
  - 수기/엑셀: 매장 수가 늘거나 인원이 많아지면 주휴수당 합산·대타 조율이 한계에 부딪힌다.
  - 범용 스케줄러(구글 캘린더 등): 노동법 기반 수당 계산이 없고 다점포 집계가 불가능하다.
  - 대형 ERP(SAP, Oracle): 소·중형 사업자가 감당하기엔 비용·도입 기간이 과도하다.

### 관련 문서 / 레퍼런스

- Shiftee — https://shiftee.io/ko/scheduler
- 하우머치 (Howmuch) — 조직 생성/초대, 세금·4대보험 설정 흐름 참고
- Deputy, 7shifts — 글로벌 다점포 교대근무 SaaS 구조 참고

## 2. 목표

### 사용자가 무엇을 할 수 있어야 하는가

- **관리자**: 스케줄을 효율적으로 편성하고, 근태·급여를 한 곳에서 관리한다.
- **근무자**: 희망 근무를 앱에서 신청하고, 확정 스케줄·급여 명세를 투명하게 확인한다.
- **공통**: 수당이 자동 계산되어, 산정 기준이 양측에 동일하게 보인다.

### 정량 목표

- 주간 스케줄 편성 시간 **70% 이상 단축** (수기 편성 대비 기준)
- 급여 계산 오류 **0 지향** (주휴·야간·연장 수당 자동화)
- 관리자–근무자 간 **급여 정산 분쟁 감소**

## 4. 범위

> 페이즈 분류 기준: "이 기능 없이 핵심 루프(희망 신청 → 스케줄 확정 → 급여 정산)가 돌아가는가"

### Phase 1 — MVP: 핵심 서비스 루프 + 전체 플랫폼

**관리자 (`apps/web`, 데스크탑 전용 — 반응형 미지원)**

- [ ] 계정 및 조직 관리 (이메일+비밀번호 가입, 조직 CRUD, 다중 조직 스위칭)
- [ ] 인력 관리 (근무자 등록, 자동 발급 사번 조회, 스케줄 타입 지정, 임금명세서 템플릿 지정, 퇴사 처리)
- [ ] 스케줄 편성 (FIXED 근무자 자동 생성, FLEXIBLE 근무자 수동 배치) + 확정
- [ ] 근태 확인 (지각·연장·결근·퇴근 누락 하이라이팅, 수정 요청 승인, 관리자 직접 입력)
- [ ] 급여 계산 (기본급 + 주휴·야간·연장수당 + 공제) + 명세서 발급

**근무자 (`apps/mobile`, Expo 네이티브 앱 — iOS·Android)**

- [ ] 카카오 / 네이버 소셜 로그인 + 사번으로 조직 연결
- [ ] 근무 불가 신청 (불가/제약 입력 방식)
- [ ] 확정 스케줄 확인
- [ ] GPS 기반 출퇴근 체크 (버튼 방식)
- [ ] 근태 수정 요청
- [ ] 급여 명세 확인 + 근태 서명/동의
- [ ] Push 알림 (Expo Notifications) — 스케줄 확정·변경, 근태 수정, 명세서 발급 등

**인프라**

- [ ] AWS EC2 (NestJS API 서버)
- [ ] AWS S3 + CloudFront (Next.js 정적 호스팅)
- [ ] GitHub Actions CI/CD (테스트 자동화 + 자동 배포)

### Phase 2 — 고도화

- [ ] 관리자 웹 반응형 지원 (태블릿·모바일에서 관리자 접근 가능)

## 5. 사용자 흐름

### 5.1 사용 시나리오

**시나리오 1 — 주간 스케줄 편성 (최성민, 페르소나 A)**

> 최성민은 매주 월요일 다음 주 스케줄을 짠다. 일감에서 FLEXIBLE 근무자들의 희망 신청 마감을 확인하고, 스케줄 편성 화면에서 미충족 시간대를 확인한다. 희망 신청 내역을 참고해 시간대별로 근무자를 수동으로 배치하고 확정한다. 근무자들에게 Push 알림이 자동 발송된다.

**시나리오 2 — 급여 정산 (최성민 → 김하은, 페르소나 A·C)**

> 월말, 최성민은 근무자들의 근태를 확인한다. 김하은이 앱에서 근태 내역을 검토하고 서명하면 급여 계산이 자동으로 실행된다. 주휴수당·야간수당이 자동 계산된 명세서를 최성민이 발급하면, 김하은의 앱에 발급 알림이 전송된다. 김하은은 앱에서 항목별 계산 근거를 확인한다.

## 6. 기능 요구사항

> **조직 관리 vs 인력 관리 분리 원칙**
>
> - **조직 관리** (FR-1): 매장 자체의 설정값 풀(pool)을 정의한다 — 임금명세서 템플릿 목록, GPS 허용 반경, 근무 유형, 조직 휴무일.
> - **인력 관리** (FR-5): 근무자 개인에게 그 풀에서 값을 지정한다 — 어떤 템플릿을 쓸지, 스케줄 타입(FIXED/FLEXIBLE), FIXED의 경우 고정 스케줄.
>
> 관리자는 조직 설정에서 "사용 가능한 옵션"을 먼저 만들고, 인력 관리에서 근무자별로 "어떤 옵션을 쓸지" 지정한다.

### FR-1. 계정 및 조직 관리

> 상세 명세 → `docs/SPEC.md` FR-1

#### FR-1.1 관리자 계정

> 관리자는 이메일·비밀번호로 계정을 생성하고 관리할 수 있어야 한다.

- [ ] 이름·이메일·비밀번호로 가입하고 로그인할 수 있다.
- [ ] 이메일로 비밀번호 재설정을 요청할 수 있다.
- [ ] 소속 조직을 모두 삭제한 후 탈퇴할 수 있으며, 근태·급여 이력은 3년 보존된다.

#### FR-1.2 근무자 계정

> 근무자는 카카오 또는 네이버 소셜 로그인으로 가입·로그인할 수 있어야 한다.

- [ ] 카카오/네이버 OAuth로 최초 가입과 재로그인이 가능하다.
- [ ] 미정산 급여가 있으면 정산 완료 전까지 탈퇴가 불가하다.

#### FR-1.3 조직 생성

> 관리자는 매장 정보와 운영 조건을 입력해 조직을 생성할 수 있어야 한다.

- [ ] 사업자번호·조직명·위치(도로명주소)·GPS 허용 반경·근무 유형을 설정할 수 있다.
- [ ] 조직 휴무일을 설정할 수 있다.

#### FR-1.4 조직 수정

> 관리자는 조직 설정을 언제든 수정할 수 있어야 한다.

- [ ] 조직 생성 시 입력한 항목(사업자번호 제외)을 수정할 수 있다.

#### FR-1.5 조직 삭제

> 관리자는 더 이상 운영하지 않는 조직을 삭제할 수 있어야 한다.

- [ ] 소속 근무자 전원 퇴사 처리 후에만 삭제할 수 있다.
- [ ] 삭제 후 근태·급여 데이터는 3년 보존된다.

#### FR-1.6 다중 조직 관리

> 다점포 관리자는 한 계정으로 여러 조직을 전환하며 관리할 수 있어야 한다.

- [ ] 한 계정으로 여러 조직을 생성하고 운영할 수 있다.
- [ ] 조직 전환 즉시 해당 조직의 데이터로 컨텍스트가 전환된다.

### FR-2. 스케줄 관리

> 상세 명세 → `docs/SPEC.md` FR-2

#### FR-2.1 근무 불가 신청

> FLEXIBLE 근무자는 안되는 날짜와 시간대만 앱에서 입력할 수 있어야 한다.

- [ ] 신청 기간 내 날짜별로 불가 / 시간 제약을 입력할 수 있다.
- [ ] 미입력 날짜는 전일 근무 가능으로 자동 처리된다.
- [ ] 마감 전까지 수정 가능하며, 마감 후에는 입력이 비활성화된다.

#### FR-2.2 스케줄 확정 및 알림

> 관리자는 신청 마감 후 스케줄을 배치하고 확정할 수 있어야 한다.

- [ ] 확정 시 스케줄 상태가 DRAFT → PUBLISHED로 변경된다.
- [ ] 확정과 동시에 해당 근무자에게 Push 알림이 발송된다.
- [ ] 확정과 동시에 해당 근무자의 근태 레코드가 자동 생성된다.

#### FR-2.3 FIXED 스케줄 생성

> 관리자는 고정 근무자의 요일별 근무 패턴을 한 번 설정하면 스케줄이 자동으로 생성되어야 한다.

- [ ] 요일별 시작·종료 시간을 설정하면 지정 기간에 스케줄이 자동 생성된다.
- [ ] 조직 휴무일은 자동 제외된다.
- [ ] 변경 반영 시점을 선택할 수 있다.

### FR-3. 근태 관리

> 상세 명세 → `docs/SPEC.md` FR-3

#### FR-3.1 GPS 기반 출퇴근 체크

> 근무자는 앱에서 버튼 한 번으로 출퇴근을 기록할 수 있어야 한다.

- [ ] 출근 체크는 조직의 GPS 허용 반경 내에서만 가능하다.
- [ ] 퇴근 시 일반 퇴근 또는 연장 근무를 선택할 수 있다.

#### FR-3.2 근태 예외 하이라이팅

> 관리자는 정상 처리되지 않았거나 확인이 필요한 근태를 화면에서 한눈에 파악할 수 있어야 한다.

- [ ] 지각·연장·결근·퇴근 누락 항목이 하이라이팅된다.
- [ ] 수정 요청 대기 항목이 하이라이팅된다.

#### FR-3.3 근태 수정 요청

> 근무자는 잘못 기록된 근태를 수정 요청할 수 있어야 한다.

- [ ] 출근/퇴근 시각과 사유를 입력해 수정 요청을 제출할 수 있다.
- [ ] 관리자 승인 시 근태 레코드가 업데이트되고 감사 로그가 보존된다.
- [ ] 관리자 거절 시 기존 기록이 유지되고 근무자에게 알림이 발송된다.

#### FR-3.4 관리자 직접 입력

> 관리자는 예외 상황 시 근무자의 출퇴근 시각을 직접 입력할 수 있어야 한다.

- [ ] 관리자가 직접 입력한 내역은 감사 로그에 별도 기록된다.
- [ ] 직접 입력 후 해당 근무자에게 변경 알림이 발송된다.

#### FR-3.5 근태 확정 및 서명

> 근무자는 정산 전 자신의 근태 내역을 확인하고 동의할 수 있어야 한다.

- [ ] 정산 기간의 근태 목록을 조회하고 서명(동의)할 수 있다.
- [ ] 결근·퇴근 누락 항목이 있으면 서명이 차단된다.
- [ ] 서명 즉시 급여 계산이 자동으로 트리거된다.
- [ ] 서명 후 근태 수정이 승인되면 서명이 초기화되고 재서명이 필요하다.

### FR-4. 급여 계산 엔진

> 상세 명세 → `docs/SPEC.md` FR-4

#### FR-4.1 급여 자동 계산

> 근무자 서명 완료 후, 확정 근태와 임금명세서 템플릿을 기반으로 급여가 자동 계산되어야 한다.

- [ ] 기본급·주휴수당·야간·연장수당·공제 항목이 템플릿 설정에 따라 자동 계산된다.
- [ ] 임금명세서 템플릿이 지정되지 않은 경우 계산이 차단된다.

#### FR-4.2 급여 계산 트리거

> 근무자가 서명하는 즉시 급여 계산이 자동으로 시작되어야 한다.

- [ ] 근무자 서명 시 해당 근무자의 급여 계산이 자동 실행된다.
- [ ] 여러 근무자가 동시에 서명한 경우 병렬로 처리된다.

#### FR-4.3 급여 명세서 발급

> 관리자는 급여 계산 결과를 명세서로 발급할 수 있어야 한다.

- [ ] 계산 완료된 근무자에 대해 발급 전 추가 지급·공제 항목을 입력할 수 있다.
- [ ] 계산 완료된 근무자에 대해 명세서를 발급할 수 있다.
- [ ] 발급 즉시 근무자에게 Push 알림이 발송된다.
- [ ] 근무자는 앱에서 기본급·수당·공제·실수령액을 항목별로 조회할 수 있다.

#### FR-4.4 급여 계산 감사 로그

> 관리자는 급여 계산 이력을 추적할 수 있어야 한다.

- [ ] 급여 계산 실행마다 계산 시각·기준 스냅샷·결과가 기록된다.
- [ ] 재계산 시 별도 이력이 남으며, 3년 보존된다.

### FR-5. 인력 관리

> 상세 명세 → `docs/SPEC.md` FR-5

#### FR-5.1 근무자 등록

> 관리자는 근무자를 조직에 등록하고 스케줄 타입·급여 조건을 설정할 수 있어야 한다. 사번은 등록 완료 시 시스템이 자동 발급한다.

- [ ] 이름·입사일·스케줄 타입을 입력해 근무자를 등록할 수 있다.
- [ ] 사번은 조직 코드 기반으로 자동 발급되며 관리자가 입력하거나 수정할 수 없다.
- [ ] FIXED 선택 시 요일별 근무 시간과 변경 반영 시점을 추가 설정한다.
- [ ] 임금명세서 템플릿은 등록 시 선택 입력하며, 나중에 지정할 수 있다.
- [ ] 근무자는 소셜 로그인 후 사번을 입력해 조직과 연결한다.

#### FR-5.2 퇴사 처리

> 관리자는 계약이 종료된 근무자를 퇴사 처리할 수 있어야 한다.

- [ ] 미정산 급여가 있으면 명세서 발급 완료 전까지 퇴사 처리가 차단된다.
- [ ] 퇴사 처리 시 해당 조직에 대한 접근이 불가해진다.
- [ ] 확정된 미래 스케줄은 취소 처리된다.

#### FR-5.3 임금명세서 템플릿 관리

> 관리자는 조직 단위로 임금명세서 템플릿을 생성·수정·삭제하고 근무자별로 지정할 수 있어야 한다.

- [ ] 급여 타입(시급/일급/월급)·금액·세금 유형·야간·연장수당 배율·정산 기간·지급일을 설정할 수 있다.
- [ ] 이미 근무자에게 지정된 템플릿은 삭제 시 소프트 딜리트 처리된다.
- [ ] 급여 계산 시 계산 시점의 템플릿 값이 스냅샷으로 저장된다.

### FR-6. 대시보드

#### FR-6.1 관리자 대시보드

> 관리자는 스케줄·근태·급여·인력 관리를 웹 대시보드 한 곳에서 처리할 수 있어야 한다. 여러 시스템을 오가지 않고 업무를 효율적으로 처리하기 위해서다.

**Acceptance Criteria**

- [ ] 조직 홈에서 다중 조직 전환, 근무자 수, 현재 근무 중인 근무자 수, 처리 필요 건수를 확인할 수 있다.
- [ ] 스케줄 편성: FLEXIBLE 근무자 희망 신청 취합 → 수동 배치 → 확정을 할 수 있다. FIXED 근무자는 설정 기반으로 스케줄이 자동 생성된다.
- [ ] 근태 관리: 지각·연장·`ABSENT`·`MISSING_CHECKOUT` 하이라이팅, 수정 요청 승인/거절, 관리자 직접 입력을 할 수 있다.
- [ ] 급여 정산: 근무자 서명 후 자동 계산된 급여를 확인하고 명세서를 발급할 수 있다.
- [ ] 인력 관리: 근무자 등록·자동 발급 사번 조회·퇴사 처리, 임금명세서 템플릿 CRUD·근무자별 지정, 조직 설정 수정을 할 수 있다.
- [ ] 데스크탑 전용 (반응형 미지원, `apps/web`).

#### FR-6.2 근무자 앱

> 근무자는 모바일 앱 하나로 근무 관련 모든 작업을 처리할 수 있어야 한다. 별도 시스템 없이 스마트폰으로 편리하게 근무를 관리하기 위해서다.

**Acceptance Criteria**

- [ ] 소셜 로그인 후 사번을 입력해 조직에 연결할 수 있다.
- [ ] FLEXIBLE 근무자는 근무 불가 신청 기간에 불가 날짜·시간 제약을 입력할 수 있다.
- [ ] 확정된 스케줄을 주간·월간 뷰로 확인할 수 있다.
- [ ] GPS 기반 출근 체크, 일반 퇴근·연장 근무 선택 퇴근 체크를 할 수 있다.
- [ ] 잘못 기록된 근태에 대해 수정 요청(시각·사유)을 제출할 수 있다.
- [ ] 정산 기간의 근태 목록을 확인하고 서명(동의)할 수 있다. 급여 명세서를 항목별로 조회할 수 있다.
- [ ] Push 알림(스케줄 확정·변경, 근태 수정 결과, 명세서 발급)을 수신할 수 있다.
- [ ] iOS·Android 네이티브 앱(Expo)으로 제공된다 (`apps/mobile`).

## 7. 비기능 요구사항

- **성능**:
  - 스케줄 화면 LCP(최대 콘텐츠 풀인트) **2.5초 이하**
  - 급여 계산 응답 **1초 이하**
- **플랫폼**:
  - 관리자: 데스크탑 웹 (`apps/web`, 반응형 미지원)
  - 근무자: Expo 네이티브 앱 (`apps/mobile`, iOS·Android)
- **접근성**: 모바일 최소 폰트 14px, 명도 대비 WCAG AA 기준.
- **보안**: 급여·개인정보 암호화, 조직 간 데이터 격리(Row-level security), 사업자번호 검증.
- **정확성/규정**: 노동법 기반 수당 계산 정확성 — 최저임금·주휴수당·공휴일 규정 변경 시 엔진 업데이트 대응.
- **로깅/모니터링**: 급여 계산 감사 로그, 스케줄 변경 이력 추적, 관리자 직접 입력 이력 추적.

## 8. 리스크

> 기술 구현 리스크는 `docs/TEST_PLAN.md`에서 관리한다.

- **Cold start 문제**: 양면 플랫폼 특성상 관리자가 없으면 근무자 유입도 없다. 초기 관리자 확보 전략 없이는 플랫폼이 작동하지 않으며, 관리자 온보딩에 집중하는 초기 런칭 전략이 필요하다.
- **전환 저항**: 엑셀·수기 방식에 익숙한 소상공인이 새 도구 도입을 꺼릴 수 있다. 온보딩 과정에서 마찰이 크면 이탈로 이어지므로 초기 설정 흐름을 최대한 단순하게 설계해야 한다.
- **경쟁 서비스 대응**: Shiftee 등 기존 서비스 대비 수당 자동 계산과 근무자-관리자 간 투명성이라는 차별점이 실제로 체감되지 않으면 전환 동기가 약하다.
- **노동법 변경 리스크**: 최저임금 인상, 주휴수당 기준 변경 등 법 개정 시 급여 엔진 업데이트가 지연되면 계산 오류가 발생해 신뢰도에 직접 타격이 간다. 법 개정 모니터링과 신속 대응 체계가 필요하다.
